# FieldShield architecture

## Overview

FieldShield is a single-page React + TypeScript application built with Vite. It runs entirely in the browser, stores data in IndexedDB and is installable as a Progressive Web App (service worker generated by `vite-plugin-pwa` / Workbox). There is no server.

```
┌──────────────────────────── UI (src/modules, src/components) ─────────────────────────────┐
│ Dashboard │ Mission Control │ Measure │ Photos │ Notes & Report │ Estimate QC │ Export │ … │
└──────────────┬────────────────────────────────────────────────────────────────────────────┘
               │ useStore() / useInsp()  (React context)
┌──────────────▼─────────────── State (src/state/store.tsx) ────────────────────────────────┐
│ In-memory inspections + settings; every update = clone → mutate → save (serialised queue)  │
│ Save status shown in the header; quota errors surfaced to the user                         │
└──────────────┬────────────────────────────────────────────────────────────────────────────┘
               │ DataStore interface (src/data/repository.ts)
┌──────────────▼──────────── Offline Storage Manager (src/data/indexedDb.ts) ───────────────┐
│ IndexedDB stores: inspections · blobs (photos) · settings · tutorials                      │
└───────────────────────────────────────────────────────────────────────────────────────────┘

Pure services (src/services) — no UI, fully unit-tested:
  inspectionRecord  Inspection Record Manager (factories, history, labels)
  checklists        Configurable templates, progress
  measurement/units Measurement & Calculation Engine
  validation        Validation & Completeness Engine (gaps + consistency)
  photos            Evidence & Relationship Manager (originals, thumbnails, suggestions, annotation)
  reportGenerator   Report generator (data-only narratives, damage table, versioning)
  estimateImport    CSV parsing + column mapping
  estimateQC        Estimate Review Rules Engine
  exports           Report & Export Generator (PDF, CSV, ZIP, backup)
  workflow          13-step workflow tracker
  demo/demoImages   Fictional demonstration inspection + synthetic images
Tutorial system (src/tutorial) — Interactive Tutorial & Help System
```

## Shared data model

All five modules read and write one aggregate, `Inspection` (`src/domain/models.ts`), validated with zod:

- `property`, `structures[]`, `areas[]` (elevation / roof / roof plane / room / exterior feature / other; each with its own photo checklist)
- `checklist[]` — `ChecklistItem` (phase, status, user-set `required`, area link)
- `observations[]` — `Observation` (kind, condition, component, area, `photoIds[]`, `measurementIds[]`)
- `roofPlanes[]`, `roofLines[]`, `rooms[]` — measurements; every dimension stored **as entered** (`{value, unit}`), with `source` (measured / estimated / imported) and `revisions[]` recording changes to original values
- `photos[]` — `Photo` metadata (blob keys, original vs derived copy, suggestion state); binaries live in the `blobs` store
- `annotations[]` — `PhotoAnnotation` shapes used to produce annotated copies
- `reports[]` — versioned `Report` with sections (generated vs edited text, approval), damage table, issues, and `sourceRecordIds` listing every record used
- `estimate` — `Estimate` with `EstimateLine[]`
- `findings[]` — `QCFinding` with deterministic `key` so dispositions survive re-runs; stale findings are kept
- `followUps[]`, `history[]`, `reviews` (pre-inspection, departure, final review, last export)

`Settings` (units, inspector name, checklist template, default photo checklists, dictation opt-in) and `TutorialProgress` are stored separately. All records have stable IDs and timestamps.

Relationships are explicit IDs: observation → photos/measurements, photo → area/structure/original photo, estimate line → area, finding → related line/observation IDs, report → source record IDs.

## Key design decisions

- **Local-first.** IndexedDB via `idb`. The UI depends only on the `DataStore` interface, so a sync-capable implementation can be added later (see roadmap) without rewriting modules.
- **No fabrication.** Engines return `null` + `missing[]` for incomplete inputs. Report text is assembled only from user records and says “Not recorded” where data is absent.
- **Facts vs. interpretation.** Observation kinds are chosen by the user; the consistency engine flags cause language in direct observations, unsupported interpretations, contradictions, coverage language and unconfirmed reported damage.
- **Confirmed vs. potential.** QC findings carry `classification: confirmed_arithmetic | potential_concern`, shown and exported separately.
- **Originals preserved.** Photo originals are stored byte-for-byte; annotation produces a new `Photo` with `isOriginal: false` and `derivedFromId`.
- **Atomic imports.** CSV import and backup restore are fully parsed and validated before anything is written; photo/backup restores write images before records.
- **Hash routing.** `HashRouter` lets `dist/` be hosted on any static server, including a sub-path.
